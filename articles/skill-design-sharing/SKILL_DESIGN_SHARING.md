# Skill 设计的艺术：从提示词到工程化智能体组件

> 当我尝试让 AI 操作一套内部业务平台时，发现"写好提示词"远远不够。
> 这篇分享按"遇到什么问题 → 我怎么想 → 怎么落地"的顺序，记录每一个设计决策的来龙去脉。

---

## 一、起点：为什么 Skill 越写越长，AI 反而越来越不听话？

最初我也是按主流做法来——把所有规则、流程、注意事项写进一份 SKILL.md：

> "你是某业务平台助手。1. 使用 CLI 操作。2. 先问用户要参数。3. 执行前确认。4. 注意某字段必须先做白名单……（200 行规则）"

跑了几轮就发现：**规则越多，AI 遵守得越差。** 它会跳步骤、把字段名串到别的接口上、不问就执行。

### 为什么会这样？

我一开始以为是模型不够聪明。但换了 Claude、GPT-5、Gemini 都一样，问题就稳定地复现。最终意识到：这不是模型问题，是**结构问题**。

![注意力被稀释](./assets/skill-design/01-attention-dilution.png)

LLM 的注意力有限——并非"上下文窗口=有效注意力"。当一份 SKILL.md 塞进去 200 条规则，它能"看到"全部，但**真正能稳定遵守的只有最显眼的那几条**。中间的规则会被前后内容互相干扰，后面的规则甚至会被直接忽略。

这其实是 Transformer 注意力机制的天然特性，而非提示词写得好坏的问题。

### 真正的问题定义

不是"怎么写更好的提示词"，而是：

> **怎么设计一个让 AI 在每个时刻都只需要关注最少必要信息的执行环境？**

这一句问法的转变，决定了后面所有的设计。

---

## 二、第一刀：把"思考"和"执行"分开

### 我观察到什么

复盘那些跑偏的案例，发现 AI 失败的几乎都是同一类操作：
- 拼 HTTP 请求时漏了 header
- 写 YAML 文件时缩进错了
- 调接口时把 `userId` 写成了 `user_id`

但凡涉及到**精确格式、固定流程、确定性输出**的事，AI 表现都不稳定。
反过来，AI 真正擅长的——理解用户在说什么、判断哪个选项合适、用合适的语气回复——它做得非常好。

### 我的判断

把这两类事情**用同一个 AI 来做，就是核心错误。** 应该让 AI 做它擅长的，剩下的交给确定性的程序。

![分离思考与执行](./assets/skill-design/02-think-vs-do.png)

### 怎么落地

我在 Skill 里引入一个 **CLI 程序**作为执行层。约定：

- AI 只负责**理解 + 收集 + 决策 + 表达**
- CLI 负责**调 API + 校验 + 写文件 + 管状态**
- 两者之间**只用 JSON 通信，不用自然语言**

举个具体的对比，"创建一个资源"这个动作：

| 谁来做 | AI 直接调 API（旧） | AI → CLI（新） |
|--------|---------------------|----------------|
| 端点地址 | AI 记忆 / 提示词里写 | CLI 内置 |
| 认证 header | AI 拼 | CLI 自动加 |
| 字段名/格式 | AI 容易写错 | CLI 强类型 |
| 错误重试 | AI 看着办 | CLI 标准化 |
| 失败时返回 | 自然语言混乱 | 退出码 + JSON |

AI 这一侧只需要：

```
"调用 create_resource，参数是：name=foo, owner=bar"
```

剩下的全是 CLI 的事。**AI 的不确定性，被 CLI 的确定性包裹住了。**

### 这一刀解决了什么

- AI 不再因格式细节翻车
- 同一个 Skill 换不同模型跑，行为基本一致（因为执行层是 deterministic 的）
- CLI 可以单独测试、单独迭代——脱离 AI 也能跑通

## 三、第二刀：让 CLI 控制 AI 的"视野"

### 新的问题来了

光是分离思考和执行还不够。当流程变长（比如一个"端到端创建完整业务配置"的需求要走 5 个步骤），新问题出现了：

**把 5 个步骤一次性写进提示词时，AI 经常做完前两步就开始跑偏。**

调研后我意识到：这是上一节的注意力问题在更长流程里的放大版。
即便我已经把每个动作拆成了 CLI 调用，**"应该按什么顺序调用、每步要收集什么"这部分编排逻辑还在 AI 脑子里**——还是会被稀释、被干扰。

### 我的判断

如果"流程顺序"也是一种确定性逻辑，那它**也不该交给 AI。**

具体到这次场景：AI 不需要"看到"完整流程，它只需要"看到"自己当前应该做什么。

![步进式披露](./assets/skill-design/03-progressive-disclosure.png)

### 怎么落地

我设计了**步进式披露（Progressive Disclosure）**机制：

1. 流程不再是 SKILL.md 里的一段文字，而是**文件系统里的一组步骤文件**
   ```
   workflows/<workflow-name>/
   ├── WorkFlow.md            ← 只有名字 + 一句话描述
   └── references/
       ├── 01-collect-info.md
       ├── 02-create-main.md
       ├── 03-collect-detail.md
       ├── 04-create-detail.md
       └── 05-summary.md
   ```
   文件名前缀决定顺序。**重排步骤 = 重命名文件，不需要改任何代码。**

2. CLI 维护一个状态机，AI 通过两个命令与它交互：
   - `--start`：启动流程，CLI 返回**第 1 步的内容**
   - `--advance`：提交当前步数据，CLI 返回**下一步要做什么**

3. 关键设计：**AI 在任意时刻看到的内容，永远只有"当前步骤"。** 前面的步骤已经过去（结果会以摘要形式带过），后面的步骤还没披露。

### 这一刀解决了什么

- AI 的有效上下文从"5 步全文"压缩到"当前 1 步"，注意力高度聚焦
- 流程编排逻辑从 AI 脑子里转移到了 CLI 的状态机里——确定性 ↑
- 流程改造成本骤降：加一步 = 加一个文件；改顺序 = 改文件名

## 四、第三刀：用"门禁"约束每一步的输入

### 接下来遇到的问题

步骤拆开后，新问题又冒出来：**AI 不知道每一步到底该收集什么。**

比如"收集基础信息"这一步，AI 可能：
- 漏问了某个关键字段，下一步直接报错
- 多问了一堆和接口无关的字段，浪费用户时间
- 把字段名拼错（比如 `hostname` vs `host`），CLI 没法对应

继续观察这类失败，发现一个共同点：**每步的"完成标准"是模糊的。** AI 在自然语言指引里读到"请收集相关信息"，但什么叫"完成"，是它自己拍脑袋决定的。

### 我的判断

每一步必须有一个**明确的、机器可校验的完成契约**——而不是依赖 AI 的"判断"。

这个契约我叫它 **Gate（门禁）**：定义本步必须提交哪些字段、什么类型、是否必填。

![门禁机制](./assets/skill-design/04-gate-mechanism.png)

### 怎么落地

每个步骤文件的 YAML 头里声明 gate schema：

```yaml
---
id: collect-info
type: interactive
gate:
  schema:
    name:  { type: string, required: true, desc: "资源名称" }
    owner: { type: string, required: true, desc: "归属人" }
    scope: { type: string, required: false, desc: "可选作用域" }
---
```

下面的 markdown 正文是给 AI 的自然语言指引。

当 AI 调用 `--advance --gate-data '{...}'` 时，CLI 会：
1. 检查 schema 里 required 的字段是否都给了 → 没给就**拒绝推进**，并告诉 AI 缺哪些
2. 丢弃 schema 没声明的字段 → AI 不会被自然语言指引误导去收集无关信息
3. 都满足就持久化数据并推进

### 这一刀解决了什么

| 旧问题 | Gate 解决方式 |
|--------|---------------|
| AI 漏问字段 | required 校验，过不去 |
| AI 多问无关字段 | schema 没声明就被丢弃 |
| 不同模型行为不一致 | gate 是结构化契约，模型无关 |
| 字段名拼写漂移 | schema 是唯一真实来源 |

**这里有一个反直觉的点：约束越强，AI 反而越自由。** 因为它不用再"判断"什么算完成，只要把 schema 填满就行——心智负担从"决策"降到"执行"。

## 五、第四刀：状态写到磁盘，不放 AI 脑子里

### 又一个问题

到这一步，单次会话内的流程已经稳定了。但实际使用中我遇到了：

- 用户做到一半 IDE 崩了
- 用户晚上停了，第二天接着做
- 用户切到别的会话回来，AI 完全忘了之前做了什么

AI 没有真正的记忆。**只要会话上下文一断，前面收集的所有信息、执行的所有结果，全都丢失。**

### 我的判断

如果 AI 没有记忆，那就不要让它当"记忆"。**记忆这件事，本来就该交给磁盘。**

![状态恢复](./assets/skill-design/05-state-recovery.png)

### 怎么落地

CLI 把整个流程的运行状态写到一个 JSON 文件 `cache/workflows/<name>.state`，里面记录：

- 当前走到第几步
- 每一步收集到的 gate 数据（用户输入了什么）
- 每一步执行的结果（自动步骤调 API 返回了什么）
- 整体状态：进行中 / 已完成 / 已中止

新增一个命令：

- `--current`：返回"现在在第几步、已经完成了什么、接下来等什么"

任何时候、任何会话、任何模型——只要还能访问这个磁盘文件，就能从断点续上。

### 这一刀解决了什么

- **可恢复**：会话断了，第二天 `--current` 直接接续
- **可审计**：每步的输入输出都有记录，出问题能查到根因
- **可调试**：开发者直接打开 `.state` 文件就知道流程卡哪了
- **可移交**：用户 A 开始的流程，用户 B 接着做也没问题

更深一层，这个设计让 AI **不需要假装自己有记忆了**。它每次对话只需要问 CLI"我们到哪了"，然后专心做当下这一步。

## 六、第五刀：让步骤之间能互传数据

### 还有一个问题

步骤拆成独立文件后，一个新问题浮现：**第 2 步要用第 1 步收集的数据，怎么传？**

比如"创建资源"这个自动步骤，需要用到第 1 步收集的 `name`。最朴素的做法是让 AI 把数据带过去——但这又回到了"靠 AI 记忆"的老路上。

### 我的判断

数据流转**也是一种确定性逻辑**，应该由 CLI 处理。AI 只关心当前步的交互，不关心数据从哪来到哪去。

### 怎么落地

引入**模板变量**机制。在自动步骤的定义里直接引用前序步骤的字段：

```yaml
---
id: create-main
type: automated
automation:
  tool: create_resource
  input_mapping:
    name:  "{{gate.collect-info.name}}"
    owner: "{{gate.collect-info.owner}}"
---
```

两种引用语法：
- `{{gate.<step-id>.<field>}}` 引用前序**交互步骤**收集的用户输入
- `{{result.<step-id>.<path>}}` 引用前序**自动步骤**的 API 返回值（比如刚创建的资源 id）

CLI 在 `--advance` 推进到这一步时，从 state 文件里取出对应的值，渲染成最终的工具调用参数，然后执行。

### 这一刀解决了什么

- AI 完全不用关心数据流转——它专注当下，引擎处理上下文
- 步骤定义变成**纯声明式**——读这个文件就能知道这一步要什么、产出什么
- 步骤可以放心地**复制粘贴复用到别的工作流**——只要变量名对得上就能跑

## 七、收口：用 Skill 创建 Skill

### 最后一个问题

工作流引擎做出来后，我想再加新流程时发现：**写一个工作流要手动创建好几个文件、保证 YAML 格式正确、字段对齐——这件事本身又很容易出错。**

而这恰恰是另一个"确定性、有固定步骤"的工作。

### 我的判断

既然我已经造好了"AI 设计 + CLI 施工"的范式，**那为什么不用它来创造工作流本身？**

### 怎么落地

我做了第二个 Skill：`workflow-creator`。它的职责就是把"用户描述需求 → 生成工作流文件"的过程也工程化：

- AI 负责**需求分析**：从用户描述里拆出有几步、每步收集什么、哪些是自动步骤
- 配套的 CLI 负责**文件生成**：`init` 创建骨架，`add-step` 按格式追加步骤，`validate` 校验完整性

形成一个自洽的闭环：

> **设计**（AI + workflow-creator）→ **构建**（CLI 写文件）→ **执行**（运行时 CLI 的工作流引擎）

新工作流写完，立即能被运行时 CLI 发现并执行。整个系统从"工具"演进成了**"造工具的工具"**。

## 八、整体架构：三层分工

把前面五刀放在一起，整个 Skill 的形态浮出水面：

![三层架构](./assets/skill-design/06-three-layer.png)

每一层只做自己擅长的事，层与层之间**只用 JSON 通信**：

| 层 | 谁来做 | 解决的核心问题 |
|----|--------|---------------|
| 表现层 | AI Agent | 如何理解用户、组织表达 |
| 控制层 | CLI 中的工作流引擎 | 流程怎么走、数据怎么流转 |
| 执行层 | CLI 的原子工具调用 | 单次操作怎么稳定、可重试 |

## 九、五条设计原则（如果只能记五句话）

| 原则 | 一句话解释 | 来自哪一刀 |
|------|-----------|-----------|
| 1. AI 只做"需要理解力"的事 | 确定性操作交给 CLI | 第二节 |
| 2. AI 只看"当前必要"的信息 | CLI 控制披露节奏 | 第三节 |
| 3. 每一步要有可校验的完成契约 | Gate schema 强约束 | 第四节 |
| 4. 状态不在 AI 脑子里，在磁盘上 | 持久化 + 随时恢复 | 第五节 |
| 5. 层间只用结构化数据通信 | JSON 进 JSON 出，消灭歧义 | 全程 |

## 十、什么时候**不需要**这么设计？

工程化是有成本的。下面这些场景，老老实实写 SKILL.md 就好：

| 场景 | 建议 |
|------|------|
| 一问一答就完事的单次操作 | 普通提示词，不要过度设计 |
| 纯知识问答，不涉及执行 | 不需要状态机和 CLI |
| 步骤 ≤ 2 且无恢复需求 | 直接写在 SKILL.md 里 |
| 原型阶段，跑通优先 | 先用提示词验证，复杂度上来了再工程化 |

**判断标准**：当你发现自己在提示词里反复写"注意不要……"、"确保先……"、"必须在……之前……"——
说明你正在用自然语言模拟一个状态机。这就是工程化的拐点。
